## 2. 기술 스택 선택

### 2.1 언어: TypeScript

| 비교 항목        | JavaScript      | TypeScript          | 선택 |
| ---------------- | --------------- | ------------------- | ---- |
| 타입 안전성      | 런타임 에러     | 컴파일 타임 검증    | TS   |
| IDE 지원         | 제한적 자동완성 | 완벽한 자동완성     | TS   |
| 엔티티 관계 표현 | 주석 의존       | 인터페이스로 명확화 | TS   |
| 초기 설정        | 없음            | tsconfig 필요       | JS   |

**결정: TypeScript**

- 5개 이상의 엔티티(Student, Course, Professor, Department, Enrollment) 간 관계가 복잡
- 동시성 제어 로직에서 타입 실수 = 정원 초과 버그로 직결
- 설정 비용(5분) 대비 안정성 이점이 큼
- JavsScript와 JSDoc을 활용하는 방법도 있으나 정적 타입 분석의 이점을 살리고 interface, type 등으로 한눈에 구조가 들어온다는 장점이 있음
  - 실제로 JSDoc을 이용해서 코딩해본 결과 가독성이 TypeScript보다 떨어진다고 생각해서 JSDoc 사용 안하기로 결정

### 2.2 프레임워크: Express

| 비교 항목        | Express | NestJS                | 선택    |
| ---------------- | ------- | --------------------- | ------- |
| 설정 시간        | 3분     | 10분                  | Express |
| 학습 곡선        | 낮음    | 높음 (DI, 데코레이터) | Express |
| 구조 강제        | 없음    | 있음                  | NestJS  |
| Swagger 자동화   | 수동    | 내장                  | NestJS  |
| 과제 규모 적합성 | 적합    | 오버스펙              | Express |

**결정: Express**

- 과제 규모(API 7개)에 NestJS는 오버엔지니어링
- 빠른 설정으로 핵심 로직(동시성 제어)에 집중
- API 문서는 Markdown으로 수동 작성

### 2.3 데이터베이스: 인메모리 (Map)

| 비교 항목     | 인메모리 (Map)   | SQLite + Prisma  | PostgreSQL   |
| ------------- | ---------------- | ---------------- | ------------ |
| 설치          | 불필요           | 불필요           | Docker 필요  |
| 설정 시간     | 0분              | 10분             | 30분         |
| 학습 곡선     | 없음             | ORM 학습         | ORM + Docker |
| 동시성 제어   | 코드로 직접      | 트랜잭션         | Row Lock     |
| 데이터 영속성 | 재시작 시 초기화 | 파일/메모리 선택 | 영구 저장    |
| 평가자 실행   | `npm start`      | `npm start`      | Docker 필요  |

**결정: 인메모리 (Map)**

- 평가 환경에서 추가 설치 없이 즉시 실행 가능
- 데이터 규모(~10MB)는 Node.js 힙 메모리(1.5GB)의 1% 미만
- 서버 재시작 시 초기화 = 매번 깨끗한 테스트 환경 (오히려 장점)
- 동시성 제어를 코드로 직접 구현

### 2.4 동시성 제어: async-mutex

| 비교 항목        | async-mutex | DB Lock  | Redis 분산 락 |
| ---------------- | ----------- | -------- | ------------- |
| 설치             | npm 1개     | ORM 필요 | Redis 필요    |
| 구현 복잡도      | 낮음        | 중간     | 높음          |
| 성능             | 빠름        | DB 의존  | 네트워크 지연 |
| 단일 서버 적합성 | 최적        | 적합     | 오버스펙      |

**결정: async-mutex**

- 단일 서버 환경에서 가장 효율적
- 강좌별 Mutex로 세밀한 락 제어 가능
- 코드 레벨에서 동시성 제어 로직이 명확히 드러남

## 3. 설계 결정

### 3.1 데이터 모델

#### 엔티티 관계도

```
Department (학과)
    ↓ 1:N
Professor (교수) ←─── 1:N ───→ Course (강좌)
                                  ↓
                                  │ N:M (Enrollment을 통해)
                                  ↓
Student (학생) ←─── 1:N ───→ Enrollment (수강신청)
    ↓ N:1
Department (학과)
```

#### 엔티티 정의

| 엔티티 | 필드 | 설명 |
|--------|------|------|
| Department | id, name | 학과 정보 |
| Professor | id, name, departmentId | 교수 정보, 학과 소속 |
| Student | id, name, departmentId, grade | 학생 정보, 학과 소속, 학년(1~4) |
| Course | id, name, professorId, departmentId, credits, capacity, enrolled, schedule | 강좌 정보 |
| Enrollment | id, studentId, courseId, enrolledAt | 수강신청 내역 |

### 3.2 시간표 슬롯 정의

**결정: 요일 + 교시 조합 문자열 방식**

| 요일 | 코드 |
|------|------|
| 월~금 | MON, TUE, WED, THU, FRI |

| 교시 | 시간 |
|------|------|
| 1교시 | 09:00-10:30 |
| 2교시 | 10:30-12:00 |
| 3교시 | 12:00-13:30 |
| 4교시 | 13:30-15:00 |
| 5교시 | 15:00-16:30 |
| 6교시 | 16:30-18:00 |

**슬롯 표현 예시**: `"MON_1"`, `"TUE_3"`

**선택 근거**: 요일과 교시가 한눈에 알아보기 쉬움

**학점별 슬롯 배정**:
- 3학점: 2슬롯 (예: `["MON_1", "WED_1"]`)
- 2학점: 1~2슬롯
- 1학점: 1슬롯

**충돌 판단**: 두 강좌의 슬롯 배열에 겹치는 요소가 있으면 충돌

### 3.3 초기 데이터 생성

| 항목 | 수량 | 분배 |
|------|------|------|
| 학과 | 10개 | - |
| 교수 | 100명 | 학과당 10명 |
| 학생 | 10,000명 | 학과당 1,000명 |
| 강좌 | 500개 | 교수당 5개 |

**학점 분포**: 1학점 10%, 2학점 30%, 3학점 60% (한국 대학 보편적 분포)

**정원 범위**: 20~50명 (한국 대학 보편적 범위)

### 3.4 인메모리 DB 구조

```
Database (싱글톤)
├── departments: Map<number, Department>
├── professors: Map<number, Professor>
├── students: Map<number, Student>
├── courses: Map<number, Course>
└── enrollments: Map<number, Enrollment>
```

**싱글톤 패턴 선택 이유**:
- 인메모리 DB는 여러 인스턴스 생성 시 데이터 불일치 발생
- 모든 서비스가 동일한 데이터 소스를 공유해야 함
- 동시성 제어를 한 곳에서 일관되게 적용 가능

**Map 자료구조 선택 이유**:
- O(1) 조회 성능
- ID 기반 빠른 접근
- 삭제/수정 용이

### 3.5 Repository 계층 설계

**결정: 함수 기반 Repository 패턴**

| 비교 항목 | 클래스 기반 | 함수 기반 | 선택 |
|-----------|-------------|-----------|------|
| 구조 | class + 메서드 | export function | 함수 |
| 의존성 주입 | 생성자 주입 | 모듈 import | 함수 |
| 테스트 | Mock 클래스 필요 | jest.mock으로 간단 | 함수 |
| 코드량 | 많음 | 적음 | 함수 |

**선택 근거**:
- 과제 규모에 클래스 기반은 오버엔지니어링
- Named export로 필요한 함수만 import 가능
- CLAUDE.md 코드 컨벤션과 일치 (Named Export 사용)

**Repository 역할**:
- 데이터 접근 로직 캡슐화
- Service와 Database 사이의 중개자
- 저장소 교체 시 Service 코드 변경 불필요

### 3.6 Seed 데이터 생성 전략

**결정: 결정론적(Deterministic) 생성**

| 비교 항목 | 랜덤 생성 | 결정론적 생성 | 선택 |
|-----------|-----------|---------------|------|
| 재현성 | 불가 | 가능 | 결정론적 |
| 디버깅 | 어려움 | 용이 | 결정론적 |
| 테스트 일관성 | 낮음 | 높음 | 결정론적 |
| 다양성 | 높음 | 제한적 | 랜덤 |

**선택 근거**:
- 서버 재시작 후에도 동일한 ID로 동일한 데이터 보장
- "학생 ID 5번에서 에러 발생" → 재현 가능
- 평가자 환경에서도 동일한 결과

**구현 방식**:
- 인덱스 기반 이름 생성: `index % LAST_NAMES.length`
- 학점 분포: `index % 10`으로 1:3:6 비율 유지
- 시간표 슬롯: 교수별 충돌 방지하며 순차 배정

### 3.7 비즈니스 규칙

| 규칙 | 설명 |
|------|------|
| 최대 학점 | 학생당 18학점까지 신청 가능 |
| 시간표 충돌 | 같은 시간대에 두 개 강좌 불가 |
| 정원 제한 | enrolled < capacity 인 경우에만 신청 가능 |
| 중복 신청 | 동일 강좌 중복 신청 불가 |

### 3.8 추가 결정 사항

#### 학생 목록 학과별 필터링

- **필수 요구사항 여부**: 필수 아님 (요구사항 문서에서 학생/교수 목록의 학과별 필터링을 명시하지 않음)
- **추가 이유**
  - 테스트 및 검증 편의성: 특정 학과 학생을 빠르게 조회하여 유효한 ID 확인 가능
  - 설계 일관성: 강좌 목록에서 학과별 조회를 제공하므로 유사한 조회 패턴 유지
  - 구현 비용 대비 효과: 기존 Repository에 학과별 조회 함수가 존재해 부작용 없이 확장 가능

## 6. Trade-off 요약

| 결정        | 장점               | 단점             | 선택 이유          |
